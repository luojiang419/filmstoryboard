# 准备资产复刻分镜：开源方案调研与可行性评估

调研日期：2026-08-17

## 1. 结论先行

当前“准备资产 → 一键替换产品”的主要问题不是提示词强度不足，而是视觉条件设计存在结构性冲突：系统把包含原人物、原服装和原产品像素的完整原帧，与新人物、新产品参考图一起交给同一个多图编辑模型，再依赖长篇文字要求模型“只继承构图、不要继承主体”。这类要求在生成模型内部没有真正的像素级隔离机制，因此原人物/原产品泄漏、新旧特征融合、产品细节平均化都属于可预期结果。

综合当前实测、代码和开源项目能力，结论如下：

- **仅继续优化提示词：不可作为生产级解决方案。** 可以降低部分错误概率，但无法消除原主体泄漏，也无法稳定复原服装接缝、口袋、裤脚轮廓等细节。
- **现有 Gemini 生成接口 + 输入预处理改造：中等可行。** 通过完整性校验、原帧主体移除、单主体裁切、原比例输出和细节图拆分，可以明显改善，但精确产品复刻仍没有硬保证。
- **引入开源的结构化条件控制：可行，且是正确方向。** 构图/姿态应由骨架、深度、边缘、分割布局控制；人物身份与产品外观应通过独立编码器、遮罩和区域控制注入。
- **推荐最终形态：混合两阶段流水线。** 第一阶段生成干净场景/布局，第二阶段按遮罩分别植入人物和产品，再进行脸部与产品局部细节回填；不要让一张完整原帧同时承担构图、人物、服装、产品和色彩五种互相冲突的职责。

## 2. 当前版本的本地实测证据

本次读取了测试工程 `D:\Program Files\filmstoryboard\data\project\A` 的最近一轮复刻记录，不涉及 API 密钥。

### 2.1 实际请求配置

- 模型：`gemini-3-pro-image`
- 输出：`16:9`、`2K`
- 最近 12 个镜头提示词长度：约 1988～2677 个字符
- 镜头 1 输入了 3 张图：原帧、人物资产、产品资产
- 原帧尺寸：`419 × 314`，接近 4:3
- 输出尺寸：`2752 × 1536`，16:9
- 产品资产：`6000 × 2260` 的五视图长拼图
- 人物资产：`2752 × 1536` 的三视图拼图，人物身上已经穿着相似牛仔裤

这组输入同时存在四个冲突：

1. 提示词要求“保持原画幅”，请求参数却强制 16:9，实际输出已经改变取景与主体占比。
2. 原帧包含原人物和原产品的完整 RGB 像素，新资产又包含另一套人物和产品像素。
3. 人物资产不是纯身份图，而是带服装的三视图；产品资产也是多视图拼图，模型需要自行决定使用哪个局部。
4. 替换产品与原产品同属蓝色牛仔裤，语义高度接近，缺少遮罩和实例特征时很容易发生结构平均化。

### 2.2 “偶尔带入原人物”并不完全是随机现象

最近 12 个镜头中，镜头 5 和镜头 7 的 `asset_ids_json` 只包含产品资产，没有人物资产；当前控制器只在“参考图总数为 0”时阻止生成，并不会检查原画面里有人时是否已绑定人物替换资产。

因此这两个镜头虽然提示词写了“不得复刻原人物”，模型却没有任何新人物身份可用，只能从原帧重建人物。实测结果确实延续了原画面中的棕发女性身份，而不是目标人物资产中的金发女性。

结论：至少一部分所谓“偶发原人物泄漏”，实际是**资产绑定不完整仍被允许提交**造成的确定性失败。

### 2.3 产品细节损失的实测表现

目标产品资产具有明显的波浪形前袋口、波浪形裤脚、特定后袋形状和明线结构。生成结果大多只保留了“蓝色高腰阔腿牛仔裤”这一语义类别：

- 波浪形裤脚经常变成普通直边或极弱锯齿；
- 前袋、后袋轮廓和装饰线被重新设计；
- 腰头、门襟、裤脚长度及裤腿比例不稳定；
- 人物资产自带的牛仔裤与产品资产发生特征融合。

这说明模型学到了产品类别，但没有稳定保留产品实例身份。

## 3. 代码层根因

### 3.1 完整原帧始终作为第一张参考图

`lib/features/replicate/application/replicate_controller.dart` 的 `_generateReplicatedShot` 将输入固定组织为：

```text
原视频帧 → 可选 DWPose → 人物/产品/细节资产
```

完整原帧不是结构图，而是包含原主体身份与外观的强视觉条件。后续提示词再长，也无法保证模型只读取构图 token 而忽略人物和产品 token。

### 3.2 只有文本角色，没有机器可执行的区域角色

Gemini 请求按顺序发送图片，APIMart 请求则发送一个 `image_urls` 数组。两者都没有在 API 数据结构中携带以下信息：

- 哪张图只控制身份；
- 哪张图只控制服装；
- 哪张图只控制产品局部；
- 每个主体应影响画面中的哪个区域；
- 原帧中哪些像素必须被排除。

目前所有角色语义都压在一段约 2000～2700 字的提示词中，属于软约束。

### 3.3 不校验每个可见主体是否完成替换绑定

当前代码只在 `references.isEmpty` 时失败。只要绑定了任意一张产品图，即使画面中有人但人物槽为空，也会继续生成。

应该改为：原帧分析出 N 个人物、M 个产品后，每个主体都必须处于以下三种显式状态之一：

- 使用绑定替换资产；
- 明确保留原主体；
- 明确移除该主体。

任何“未决定”状态都不得提交。

### 3.4 原画幅与生成画幅冲突

当前默认优先选择 16:9，而测试原帧为 4:3。提示词要求严格保持画幅和构图，但请求参数会迫使模型重新构图。复刻模式应默认锁定最接近原帧宽高比的模型选项，并在无法精确匹配时显示裁切预览。

### 3.5 参考资产没有进行单主体规范化

当前测试资产是多视图横向拼图：人物三视图、产品五视图。对 Gemini 直连通道，本地图还会缩至最长边 1536，并在需要时压缩为不超过约 900KB 的 JPEG。对于 `6000 × 2260` 产品拼图，缩放后每个视图只占约 300 像素宽，细节证据显著减弱。

复刻资产应该先拆成独立参考：

- 人脸/身份近景；
- 人物全身无干扰图；
- 产品正面、背面、侧面独立图；
- 接缝、口袋、边缘、材质独立局部图；
- 每张图附带主体遮罩或透明背景。

## 4. 成熟开源项目对比

| 项目 | 核心机制 | 官方效果侧重 | 对当前问题的帮助 | 主要限制 | 建议定位 |
|---|---|---|---|---|---|
| [Story2Board](https://github.com/DavidDinkevich/Story2Board) | Latent Panel Anchoring + 注意力 value 混合 | 多镜头人物一致、场景和构图多样性 | 可用于后续跨镜头一致性 | 不做精确原帧复刻，也不解决产品实例替换；基础模型的属性串位仍会被传播 | 后期一致性模块，不是当前首要修复 |
| [StoryDiffusion](https://github.com/HVision-NKU/StoryDiffusion) | 一致性自注意力 | 漫画/故事中的人物连续性 | 可降低人物跨镜头漂移 | 更偏人物与风格一致，不提供产品遮罩式替换 | 作为人物连续性基线 |
| [StoryMaker](https://github.com/FireRedTeam/StoryMaker) | 人脸身份 + 裁切人物特征 + 分割遮罩约束注意力区域 + 可选姿态 ControlNet | 脸、发型、服装、身体一致，多人物 | 直接证明“主体裁切 + 遮罩隔离 + 姿态解耦”比纯多图提示更合理 | 论文明确承认服装细节仍不理想，三人以上困难 | 人物分支的重要参考 |
| [InstantID](https://github.com/instantX-research/InstantID) | Face ID embedding + IdentityNet/ControlNet | 单图零训练的人脸身份保持 | 可独立锁定人物身份，避免从原帧复制脸 | 只解决人脸身份，不保证服装和产品 | 人脸精修或人物身份分支 |
| [ControlNet](https://github.com/lllyasviel/ControlNet) + [IP-Adapter](https://github.com/tencent-ailab/IP-Adapter) | 姿态/深度/边缘等结构控制 + 图像特征控制 | 结构与外观条件可分别调权重 | 能把“原帧构图”转换为不含身份的结构条件 | 通用 IP-Adapter 对产品精细实例仍可能只保留语义 | 最成熟、最容易验证的结构化基线 |
| [OminiControl](https://github.com/Yuanshi9815/OminiControl) | FLUX 上统一的 subject、edge、depth、inpaint 条件，可调 condition scale | 主体驱动 + 空间对齐控制 | 同一框架可分别承接产品主体和原帧结构，最接近所需架构 | FLUX 本地推理较重；仍需资产裁切与遮罩 | 推荐开源主线候选 |
| [AnyDoor](https://github.com/ali-vilab/AnyDoor) | 参考物体 + 目标区域遮罩的零样本物体植入 | 物体身份保持与场景融合 | 比全图多参考更适合刚性产品替换 | 官方说明没有为虚拟试穿专门设计；遮罩质量会影响结果 | 刚性产品/道具替换基线 |
| [OSInsert](https://github.com/bcmi/OSInsert-Image-Composition) | 两阶段：先生成合理姿态/视角，再用 InsertAnything 回填参考细节 | 兼顾真实性和实例细节 | 与当前“产品结构对了但细节丢失”高度匹配 | 项目较新，模型链路复杂，需要前景遮罩和目标框 | 产品高保真分支候选 |
| [Qwen-Image-Edit](https://github.com/QwenLM/Qwen-Image) | 原生多图编辑与多人物融合 | 多人物一致、工业设计和材质替换 | 可作为比当前 Gemini 更易自部署和 A/B 的编辑后端 | 官方也提示不做 prompt rewriting 时结果会不稳定；仅换后端仍不能替代遮罩和输入隔离 | 近期开源后端候选 |

### 4.1 可核验的效果信息

- Story2Board 在 DS-500 上的身份一致性 DreamSim 为 `0.7018`，高于论文对比的 DreamStory `0.6714`；但文本对齐 CLIP-T 略低（`0.3723` 对 `0.3779`）。这说明一致性与提示遵循本身存在权衡，不能只看单一指标。
- Story2Board 论文明确展示了注意力纠缠的限制：当基础模型已经把不同角色属性混在一起时，一致性机制可能把错误继续传播，而不是纠正它。这与当前人物/服装/产品混图后的特征串位一致。
- StoryMaker 使用分割遮罩分别限制不同人物及背景的交叉注意力影响区域，并用姿态条件促进外观与姿态解耦；论文同时承认服装细节仍不够理想。这说明“加人物图 + 写清楚服装”本身达不到商品级服装复刻。
- AnyDoor 官方要求目标物遮罩，且明确提醒遮罩过粗会影响结果；官方也指出其没有为虚拟试穿专门调优。
- OSInsert 不依赖一次生成完成所有目标，而是先处理姿态/视角真实性，再回填参考物体外观细节。其两阶段设计比当前单次多图请求更符合高保真产品复刻需求。
- Qwen-Image-Edit-2511 官方展示了多人物一致性和工业产品/材质编辑，并明确建议使用 prompt rewriting 提高稳定性。它适合作为候选后端，但不是“无预处理即可稳定复刻”的证明。

## 5. 推荐技术路线

### P0：先修复当前链路中的确定性错误

1. **资产完整性门禁**
   - 根据人物/产品检测结果创建主体清单。
   - 每个主体必须显式选择“替换、保留、移除”。
   - 人物槽为空但原帧有人时禁止提交。

2. **复刻模式默认沿用原比例**
   - 自动选择最接近原帧的模型比例。
   - 不允许提示词写“保持原画幅”，请求却提交 16:9。

3. **资产规范化**
   - 自动拆分多视图拼图。
   - 使用 SAM/SAM2 或现有分割服务生成主体遮罩。
   - 人物身份图、全身图、产品整体图、产品细节图分开。
   - 产品细节图不得压缩成低质量 JPEG；保留 PNG/WebP 或高质量原图。

4. **减少提示词冲突**
   - 提示词只描述可执行关系，不再重复十余次“禁止”。
   - 每张图使用一行固定角色定义。
   - 结构控制和身份控制不再共同依赖完整原帧。

### P1：把单次多图生成改为两阶段生成

建议流程：

```text
原帧
  → 人物/产品检测与分割
  → 移除原人物和原产品，得到干净场景底板
  → 从原帧提取姿态、深度、边缘、主体框和遮挡关系
  → 按遮罩植入目标人物
  → 按遮罩植入目标产品/服装
  → 人脸局部精修
  → 产品局部细节回填
  → 构图、姿态、身份、产品、无字规则自动验收
```

推荐路由：

- 人脸身份：InstantID 或同类 ID adapter；
- 人体姿态：现有 DWPose + ControlNet/OminiControl pose；
- 刚性产品、道具：AnyDoor、OSInsert 或 OminiControl inpaint；
- 可穿戴服装：专用 virtual try-on/garment warping 分支，不能只用通用物体植入；
- 场景与构图：clean plate + depth/canny/segmentation，不再使用带原主体的完整 RGB 原帧；
- 当前 Gemini/Qwen API：保留为无法本地处理时的兼容后端。

### P2：单镜头稳定后，再处理跨镜头一致性

只有单帧人物、产品和构图都通过验收后，才引入 Story2Board/StoryDiffusion 类跨镜头一致性机制。否则一致性模块会把错误人物、错误裤型或错误口袋稳定地传播到整组镜头。

## 6. 建议建立的 A/B 验收集

不能只用“看起来不错”判断改造是否有效。建议先固定 24～30 个镜头，覆盖：

- 单人 + 可穿戴产品；
- 单人 + 手持刚性产品；
- 无人物 + 单产品；
- 多人 + 多产品一一绑定；
- 大远景、小主体；
- 近景产品细节；
- 强遮挡、侧身、背身；
- 原产品与目标产品同类、颜色相近的高难度样本。

每个方案固定随机种子或至少生成 4 次，记录成功率，而不是只挑最佳图。

### 自动指标

- 原人物泄漏：生成脸与原人物脸的 ArcFace 相似度应低于目标人物相似度；
- 目标人物一致：目标人物 ArcFace/FaceNet 相似度；
- 姿态：DWPose 关键点归一化误差；
- 构图：主体框位置、尺度、深度/边缘结构相似度；
- 产品实例：实例检索特征相似度优先，辅以 DINO/CLIP；不要只用类别语义 CLIP；
- 产品局部：口袋、接缝、裤脚、门襟等关键区域的人工标注命中率；
- 画幅：输出比例与目标比例严格一致；
- 文本/Logo：OCR 检出率。

### 人工指标

每张图分别打分：

1. 原人物/原产品是否泄漏；
2. 目标人物是否正确；
3. 产品是否为同一实例，而不只是同一类别；
4. 姿态与构图是否一致；
5. 场景光影是否自然；
6. 是否达到可直接进入视频生成的分镜质量。

## 7. 与当前硬件和桌面应用的集成判断

本机为 RTX 4070 Ti SUPER 16GB：

- SDXL + InstantID + 单个 ControlNet 可作为本地验证主线，并可使用半精度/CPU offload；
- FLUX、Story2Board、OminiControl、Qwen-Image-Edit 可通过量化和分层 offload 尝试，但批量镜头吞吐会显著慢于当前云 API；
- 若把多套大模型直接塞进安装器，会显著扩大当前约 400MB 的安装包，不建议一次性内置；
- 更合理的产品形态是“可选模型包/本地工作进程/远程推理服务”三选一，并保留当前云端后端作为回退。

## 8. 最终建议

建议停止继续扩写当前 Gemini 长提示词，按以下顺序推进：

1. 先实现资产完整性门禁、原比例输出、多视图拆分和无损细节图；
2. 建立固定 A/B 验收集，测出当前基线成功率；
3. 用 ControlNet + IP-Adapter/InstantID 做最低成本结构化基线；
4. 用 AnyDoor 或 OSInsert 单独验证产品植入；
5. 用 OminiControl 或 Qwen-Image-Edit 验证统一开源后端；
6. 单帧达标后再引入 Story2Board 类跨镜头一致性。

最关键的产品决策不是“换哪个更强的提示词”，而是把“构图、人物身份、姿态、产品实例、产品细节、场景光影”从一组互相争夺注意力的图片，改造成彼此隔离、可分区、可调权重、可单独验收的条件通道。
