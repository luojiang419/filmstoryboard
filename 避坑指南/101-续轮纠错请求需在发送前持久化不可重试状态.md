# 续轮纠错请求需在发送前持久化不可重试状态

## 问题

“最多一次纠错”不能只在内存中用布尔值约束。若应用在纠错请求已经发送、但纠错结果尚未落盘时退出，数据库仍停留在“等待纠错”；重启后再次发送会造成第二次付费请求。

## 安全做法

1. 首审失败后先保存 `awaitingCorrection`，表示尚未开始纠错，可以在重启后用可靠 continuation 恢复。
2. 真正发送纠错请求前，再原子保存 `correctionInFlight`。
3. 收到纠错图并安全落盘后，才转为 `awaitingCorrectedReview`。
4. 重启遇到 `correctionInFlight` 时，不猜测上游是否已执行或计费，不重发请求；保留已有图片并给出可读诊断。

## 原因

客户端无法仅凭本地状态判断中断前的远端请求是否已经成功。没有官方幂等键或可查询任务 ID 时，任何自动重试都可能突破“最多一次”的付费上限。此时应选择保守停止，而不是伪造可恢复性。

## 回归测试

恢复测试必须断言：

- `correctionInFlight` 重启后图片生成请求数不增加；
- 审核请求数也不增加；
- 错误信息明确包含“避免重复付费纠错”。
